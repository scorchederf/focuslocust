# Codex Implementation Instructions — `ghvault` GitHub Retrieval Vault

## Purpose

Implement a second standalone generated vault named `ghvault/` inside the existing `focuslocust` repository.

The current source-first vault remains valid. `ghvault/` is a new GitHub-first, retrieval-first output designed for fast human browsing through the GitHub web UI.

This file is the implementation handoff. Be precise. Do not reinterpret the scope into a larger project.

---

## Hard requirements

### Output model

- Generate a second standalone vault at:

```text
ghvault/
```

- Do not replace the existing `vault/` output.
- Support configurable build targets:

```bash
python3 builder.py build --target source
python3 builder.py build --target ghvault
python3 builder.py build --target both
```

- Default target should be `both`.
- `ghvault/` must be cleared and rebuilt from scratch every time it is generated.
- Keep manual content outside `ghvault/` in a repository-level `manual/` folder and copy/merge it into `ghvault/manual/` during build.
- Do not add a `--add source` CLI parameter. That idea was explicitly cancelled.

### Link model

- `ghvault/` must use GitHub-compatible relative Markdown links only.
- Do not use Obsidian wikilinks in `ghvault/`.
- Do not require Dataview, DataviewJS, plugins, SQLite, graph databases, or AI.

Correct:

```markdown
[T1105 - Ingress Tool Transfer](../attack/techniques/T1105-ingress-tool-transfer.md)
```

Incorrect:

```markdown
[[kb/attack/techniques/T1105-ingress-tool-transfer|T1105 - Ingress Tool Transfer]]
```

### Scope

Include only security / IT operational reference material:

- ATT&CK material
- tools
- commands
- platforms
- topics
- capabilities
- source records
- playbooks
- verification reports

Do not ingest:

- CISSP notes
- Security+ notes
- certification study notes
- generic personal notes
- recipes or unrelated content

### Verification requirement

The user must be able to verify where information came from.

Every generated concept page should include visible provenance. Every source record page should preserve enough source material to verify extracted claims.

Use evidence model **C**:

```text
provenance table + source-record link + short useful evidence excerpt on concept pages
fuller preserved source material on source-record pages
```

Do not drop source content just because a parser does not recognise a field.

If `certutil.exe` has a detection script, analysis note, Sigma rule, Splunk query, Elastic query, IOC, block rule, or other relevant material at the bottom of the source record, the generated vault must preserve it.

Detection content is not promoted to a full `kb/detections/` architecture yet. For now:

- preserve detection material on source-record pages
- link to it from related tool / command / technique pages where possible
- do not create mature detection engineering pages until Sigma / Atomic / query support exists

### Relationship model

Relationship types:

```yaml
relationship_types:
  explicit:
    meaning: Directly present in source data.
  inferred:
    meaning: Generated by deterministic conservative local rules.
  manual:
    meaning: User-maintained mapping or override.
```

Requirements:

- Use conservative inference.
- Mark inferred relationships visibly.
- Preserve all conflicting claims.
- Flag conflicts in `_review/conflicts.md`.
- Aliases are first-class.
- External links are preserved and separated from local verification where practical.

Initial conservative inference rule:

```yaml
- id: infer-file-download-t1105
  match:
    command_contains_any:
      - "http://"
      - "https://"
      - "ftp://"
      - "wget "
      - "curl "
      - "Invoke-WebRequest"
  creates:
    relationship_type: attack_technique
    target_id: T1105
    relationship: inferred
    confidence: high
    reason: Command appears to retrieve a remote file.
```

### Commands

Generate one command page per tool/platform, not one page per command.

Example:

```text
ghvault/kb/commands/windows/certutil.md
```

Command pages must include this fixed safety notice:

```markdown
> This page contains security testing commands. Use only in authorised environments.
```

The command page should group all preserved commands/examples for that tool and include provenance for each block.

### Validation

Generate both report-only and strict validation modes.

```bash
python3 builder.py build --target ghvault
python3 builder.py build --target ghvault --strict
```

Behaviour:

- Default mode: build succeeds and writes `_build/broken-links.md`.
- Strict mode: build fails if broken relative Markdown links are found.

### Network access

The project should be local-only by default.

If a source needs network access and the file/cache is missing, the builder should fail with:

- reason
- requested URL
- expected local/cache path
- action the operator can take

Network access should require explicit config, for example:

```yaml
runtime:
  allow_network: true
```

Do not silently fetch remote content by default.

### Ollama / local AI

Do not put AI in the core build path.

Future local Ollama support may exist only as review-only enrichment:

```yaml
ghvault:
  ollama:
    enabled: false
    mode: review_only
    write_to_canonical_pages: false
```

Ollama can suggest. It must not decide. It must not write directly to canonical pages.

## Implementation notes for Codex

### Do not scrape generated Markdown

Do not build `ghvault/` by parsing files under `vault/`.

Correct pipeline:

```text
.cache source data
    ↓
source parsers
    ↓
normalised records
    ↓
relationship builder
    ↓
ghvault renderer
    ↓
ghvault/
```

Wrong pipeline:

```text
vault/*.md
    ↓
parse headings/frontmatter
    ↓
try to infer relationships
    ↓
ghvault/
```

Scraping generated Markdown is brittle and will silently break when templates change.

### Preserve unknown useful source content

Parsers should preserve both recognised fields and unknown-but-useful sections.

Recommended parser output pattern:

```yaml
normalised_fields:
  name: certutil.exe
  platform: windows
  commands: []
  attack_techniques: []
  references: []

source_sections:
  - heading: Commands
    type: commands
    content: ...
  - heading: Detection
    type: detection
    content: ...
  - heading: Notes
    type: notes
    content: ...
  - heading: Unknown Section
    type: preserved
    content: ...
```

The current renderer uses `obj.raw` as the safety net. Codex should improve individual parsers over time to expose `source_sections` explicitly rather than relying only on raw dumps.

### Keep templates simple

The first implementation writes Markdown directly in Python to avoid prematurely building a large template layer. Once the data model stabilises, move presentation into templates under:

```text
templates/ghvault/
```

Suggested future templates:

```text
templates/ghvault/tool.md.j2
templates/ghvault/command-page.md.j2
templates/ghvault/technique.md.j2
templates/ghvault/source-record.md.j2
templates/ghvault/index.md.j2
templates/ghvault/build-report.md.j2
```

### Manual content handling

Because `ghvault/` is deleted on every build, do not hand-edit generated files inside `ghvault/`.

Put manual source content under repository-level:

```text
manual/
```

The builder copies it into:

```text
ghvault/manual/
```

Future work can add merge/override behaviour, but direct edits inside `ghvault/` should be considered disposable.

### Conflict handling

The initial renderer creates the `_review/conflicts.md` placeholder. Codex should extend conflict detection after normalised source identity rules are clearer.

Recommended conflict model:

```yaml
conflict:
  concept_id: certutil.exe
  field: description
  values:
    - source: lolbas
      value: ...
    - source: other_source
      value: ...
  action: preserve_all_and_flag
```

Do not silently choose a winner unless an explicit source-priority rule exists.

### Alias handling

Aliases are currently read from `obj.aliases`. Codex should add a first-class repository mapping file later:

```text
mappings/aliases.yml
```

Suggested shape:

```yaml
aliases:
  certutil.exe:
    - certutil
    - CertUtil
```

### Manual mapping files

Add these later when needed:

```text
mappings/
├── tools-to-techniques.yml
├── topics-to-techniques.yml
├── capabilities.yml
└── aliases.yml
```

Manual mappings must be labelled `manual` in generated relationship tables.

## Acceptance criteria

The implementation is acceptable when:

- `python3 builder.py build --target source` still builds the current source-first vault.
- `python3 builder.py build --target ghvault` builds only `ghvault/`.
- `python3 builder.py build --target both` builds both outputs.
- `ghvault/` is standalone and browsable in GitHub.
- `ghvault/` uses relative Markdown links only.
- `ghvault/` includes breadcrumbs.
- `ghvault/` includes source-record pages.
- concept pages contain visible provenance.
- source-record pages preserve raw/source material, including detection snippets/scripts.
- command pages are one page per tool/platform.
- command pages include the safety notice.
- inferred relationships are visibly marked.
- `_build/broken-links.md` is always generated.
- `--strict` fails on broken links.
- `_review/` is always generated, even when empty.
- default runtime does not silently fetch network resources.
- no CISSP, Security+, certification study notes, recipes, or unrelated content are ingested.
- no AI or Ollama output is written to canonical pages.

## Known limitations in this first implementation

This handoff implements the core renderer and CLI wiring, but Codex should improve the following after applying it to the full repository:

1. Add explicit parser-level `source_sections` instead of relying mainly on `obj.raw`.
2. Add split/per-category indexes when generated indexes become too large.
3. Add real conflict detection instead of placeholder conflict reports.
4. Add manual mapping file support.
5. Add richer platform detection for MITRE tools and non-LOLBAS/non-GTFOBins records.
6. Add source-priority configuration only if the user explicitly wants it.
7. Move Markdown rendering into `templates/ghvault/` once the data model settles.
8. Extend validation to detect orphan pages and duplicate semantic concepts, not just duplicate paths.

Do not expand scope into a database, graph engine, Dataview, or AI enrichment system.
